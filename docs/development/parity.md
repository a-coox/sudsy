# Differential testing against upstream tools

`scripts/parity.sh <tool>` runs the upstream tool and `sudsy lint` on the fixtures in `tests/parity/<tool>/` and compares the diagnostics as `(rule, line, column)`. The upstream rule name is mapped to a Sudsy rule id through the catalog (`docs/parity/<tool>.yaml`: the top-level entries whose status is `rule: <id>`); an upstream rule with no mapping is a mismatch. Every mismatch is printed (`only <tool>`, `only sudsy`) and the exit code is 1 when there is any. Run it from Git Bash.

Tools: `yamllint`, `eslint-jsonc`, `markdownlint`, `hadolint`, `shellcheck`, `psscriptanalyzer` and `stylecop` (lint mode); `prettier`, `biome`, `taplo`, `shfmt`, `buf`, `invoke-formatter`, `dotnet-format`, `csharpier` and `csharpier-xml` (format mode, below). yamllint: the script installs the catalog's `version` into a virtualenv under `target/parity/<tool>-<version>/` on first use (needs Python 3 and network) and builds the debug CLI.

## Fixtures
`tests/parity/<tool>/` holds one file per case plus the two configs that make the tools comparable: the upstream config (`.yamllint`) enables only rules Sudsy has an equivalent for, with the parameters Sudsy's rules take, and `sudsy.yaml` enables the matching Sudsy rules. A fixture is one file for every config, so the parameters must be the same for all cases. Fixtures where the tools legitimately differ are not included; those differences are recorded in the catalog entry's `gap`. Rules the formatter covers (yamllint `comments`) are off in `.yamllint`: they are tested as formatter output instead.

To add a case: add the file, enable the rule in both configs, run the script. To add a tool: add a function to `scripts/parity_compare.py` that returns the upstream diagnostics as `{(rule, line, column)}`, list the tool in `scripts/parity.sh`, and add its fixtures.

## eslint-jsonc
`scripts/parity.sh eslint-jsonc` installs ESLint 9 and eslint-plugin-jsonc at the catalog's version (`docs/parity/eslint-plugin-jsonc.yaml`) with npm into `target/parity/eslint-jsonc-<version>/` on first use (needs Node and network; PyYAML for the comparison goes into a venv below it), copies `tests/parity/eslint-jsonc/` to `work/` there so that `eslint.config.mjs` finds the plugin, and runs ESLint on every `.json` fixture. A fixture's name selects the rule and options: `eslint.config.mjs` enables one rule per fixture and `sudsy.yaml` enables the matching Sudsy rule through `overrides`, so both sides stay in step. `sorted-keys` and `sorted-array-values` report the entries that would have to move; where several shortest edits exist ESLint's pick can differ from Sudsy's, so fixtures stick to cases both agree on (the catalog `gap` says so).

## markdownlint
`scripts/parity.sh markdownlint` installs markdownlint-cli2 at the catalog's `version` with npm into `target/parity/markdownlint-<version>/` on first use, copies `tests/parity/markdownlint/` (the `.md` fixtures and a `.markdownlint.jsonc` that turns on only the rules Sudsy has an equivalent for) below it and compares `(rule, line)` of every fixture: markdownlint reports a column for some rules only, so columns are not compared. The Sudsy rule of a `rule:` status stands for the MD id of the catalog entry.

## hadolint
`scripts/parity.sh hadolint` downloads the hadolint release binary at the catalog's `version` (Windows, Linux or macOS asset) into `<target>/parity/hadolint-<version>/` on first use and runs it with `-f json` and `sudsy lint` (config: `tests/parity/hadolint/sudsy.yaml`, `preset:dockerfile/hadolint`) on the rule fixtures of the Dockerfile rules, `tests/rules/dockerfile/*/*.dockerfile` with their annotation lines removed, so the fixtures are not copied. `(rule, line)` is compared for the rules the catalog maps; hadolint's other codes (deferred DL rules, ShellCheck) are ignored. `tests/parity/hadolint/expected-diff.txt` lists known differences as `<folder>/<name> <hadolint|sudsy>:<rule> <line>: <reason>`; an entry that no longer differs fails the run. The rule fixtures are written to agree with hadolint; a case where it deliberately differs goes into the list.

## shellcheck
`scripts/parity.sh shellcheck` is the hadolint mode for shellcheck: the release archive at the catalog's `version` is downloaded into `<target>/parity/shellcheck-<version>/` on first use (zip on Windows, tar.xz elsewhere), run with `-s bash -o all -f json` (the optional checks are in the catalog, so they are on) and compared as `(rule, line)` with `sudsy lint` under `tests/parity/shellcheck/sudsy.yaml` (`preset:shell/shellcheck`) on `tests/rules/shell/*/*.sh` without annotations. `expected-diff.txt` has the same format as hadolint's.

## psscriptanalyzer
`scripts/parity.sh psscriptanalyzer` saves the PSScriptAnalyzer module at the catalog's `version` (`Save-Module`, as for invoke-formatter; needs `pwsh` and network) and runs `Invoke-ScriptAnalyzer` (`scripts/parity_psscriptanalyzer.ps1`) with the catalog's `rule:` entries that the preset `powershell/psscriptanalyzer` turns on, on the PowerShell rule fixtures (`tests/rules/powershell/*/*.ps1`, annotations removed) and the corpus (`tests/conformance/fetch-powershell-corpus.sh`), compared with `sudsy lint` (`tests/parity/psscriptanalyzer/sudsy.yaml`, that preset) as `(file, rule, line)`. It also checks that the catalog lists exactly the rules of `Get-ScriptAnalyzerRule` with the module's severities. `expected-diff.txt` has the format of hadolint's (`corpus/<path> <psscriptanalyzer|sudsy>:<rule> <line>: <reason>`; a fixture is `<folder>-<name>.ps1`); a stale entry fails. The module honors `[SuppressMessageAttribute]` and Sudsy does not, so code with one differs.

## stylecop
`scripts/parity.sh stylecop` copies `tests/parity/stylecop/` (a net10.0 project referencing StyleCop.Analyzers at the catalog's version, plus `.cs` fixtures) to `target/parity/stylecop-plain/` and `stylecop-fixed/`, enables every catalog SA id of status `rule:` or `formatter`, or `option: csharp.format.<name>` for an option the `csharp/stylecop` preset sets, as a warning through a generated `.editorconfig`, and runs `dotnet build` with an SARIF error log. Two comparisons:
- plain: each `rule:` SA id, mapped through the catalog, must be reported by `sudsy lint` at the same `(rule, line, column)`, and `sudsy lint` must report nothing else of the mapped rules;
- fixed: after `sudsy fix --unsafe .`, StyleCop must report none of those formatter ids whose coverage is `covered` (in any fixture) or `partial` (in the `layout_*` fixtures; the older fixtures show their gap), and what it still reports for `rule:` ids must match `sudsy lint`.
The fixtures' `sudsy.yaml` extends `preset:csharp/stylecop`, so the formatter ids are checked under the preset's options and the `rule:` ids with the rules the preset enables. The `layout_*` fixtures are the layout rules' violations; the `doc_*` fixtures (summary, tags, wording, text) are the SA16xx documentation rules' cases, valid C# in which every partial type has only parts that StyleCop and Sudsy judge alike (StyleCop accepts one documented part, Sudsy checks each); the run prints the formatter ids no fixture violates (the build would pass vacuously for them). Needs the .NET SDK and network for the NuGet restore. To add a case, add a `.cs` file and enable its Sudsy rules in the preset (`crates/lang-csharp/presets/stylecop.yaml`); the catalog drives the id mapping.

## Format mode
One runner (`scripts/parity_format.py`) serves every tool; a tool is an entry of `scripts/parity_format.json`, so adding one is config only (plus its `tests/parity/<tool>/` folder with `sudsy.yaml` and its `docs/parity/<name>.yaml` with the pinned `version`):
- `catalog`: the catalog file whose `version` pins the tool (`version_command` instead: the SDK's own, for `dotnet-format`); `install`: an `npm` package, a `dotnet-tool` or a `release` (URL template, per-platform `assets`: a zip, a gzip or the executable itself) and its `exe`, installed into `<target>/parity/<catalog>-<version>/` on first use;
- `command`: the tool's command line with `{prefix}`, `{exe}` and `{file}`; `input`: `arg` (the file name is an argument), `stdin`, or `in-place` (the tool rewrites a copy); `tool_may_reject`: a file the tool rejects is a difference, not an error;
- `needs`: `worker` builds the C# worker; `fetch`: scripts that fetch corpora; `fixtures`: sources of fixtures, each a `dir` (default: the tool's folder) with `suffixes`, an expected-diff name `prefix`, `recursive`, or a `list` file with `starts`; `kind: editorconfig-cases` is the `dotnet-format` layout below.

`scripts/parity.sh format prettier|biome` formats every JSON and YAML fixture in `tests/parity/<tool>/` with the tool (`prettier --no-config --no-editorconfig --embedded-language-formatting=off`, `biome format` with its defaults) and with `sudsy format`, and compares the outputs byte for byte. The tool is installed with npm at the catalog's `version` into `target/parity/<tool>-<version>/` on first use (needs Node and network); the fixtures are copied to `target/parity/<tool>-work/` first because `sudsy format` writes in place. The folder's `sudsy.yaml` extends the matching presets (`json/prettier-compat` and `yaml/prettier-compat`; `json/biome`), so a difference is a preset or formatter gap. Every difference is printed as a unified diff and the exit code is 1.

The `prettier` fixtures also include GraphQL: the folder's `.graphql` files and the corpus of `tests/conformance/fetch-graphql-corpus.sh` (`graphql/<repo>/<path>` in `expected-diff.txt`; Prettier's own tests in it include files it rejects, which count as differences unless listed, `tool_may_reject`). The `prettier` fixtures also include the folder's `.md` files, the repo's `docs/**/*.md` and the dotnet/runtime coding-guidelines docs (`tests/conformance/fetch-markdown-corpus.sh`, pinned); Prettier runs with `--embedded-language-formatting=off`, and the folder's `sudsy.yaml` sets `embedded_language_formatting: off`, because Sudsy's formatters of the fenced languages make other choices than Prettier's.

`expected-diff.txt` in the folder lists fixtures that may differ, one `<fixture>: <reason>` per line; they print as known differences and do not fail the run. An entry whose outputs are equal is reported as stale and fails the run. Fixtures named `crlf.*` keep CRLF line endings (`.gitattributes`: `-text`).

## taplo
`scripts/parity.sh format taplo` downloads the taplo release binary at the catalog's `version` (`docs/parity/taplo.yaml`) into `<target>/parity/taplo-<version>/` on first use (needs network; Windows, Linux and macOS assets), fetches the toml-test corpus and formats with `taplo fmt --no-auto-config -` and with `sudsy format` under the folder's `sudsy.yaml` (`preset:toml/taplo-compat`). The fixtures are the folder's own `*.toml`, every file of `tests/fixtures/toml/` (named `fixtures/<file>` in `expected-diff.txt`) and the valid files of the toml-test 1.0 list (`valid/...`). Outputs are compared byte for byte; `expected-diff.txt` lists the files that may differ, including those taplo itself rejects (the run counts a file taplo rejects as a difference unless listed).

## buf
`scripts/parity.sh format buf` downloads the buf release executable at the catalog's `version` (`docs/parity/buf.yaml`) into `<target>/parity/buf-<version>/` on first use (needs network), fetches the Protobuf corpus (`tests/conformance/fetch-proto-corpus.sh`) and formats each file with `buf format <file>` (it has no options) and with `sudsy format` under the folder's `sudsy.yaml` (Sudsy's defaults, no preset). The fixtures are the folder's own `*.proto` and the corpus files (`corpus/<path>` in `expected-diff.txt`). See [../formatting/protobuf.md](../formatting/protobuf.md) for the result.

`scripts/parity.sh buf` is the lint mode (hadolint's): `buf lint --error-format=json --path <fixture>` with the folder's `buf.yaml` (STANDARD) and `sudsy lint` (`preset:protobuf/buf-standard`) on `tests/rules/protobuf/*/*.proto` without annotations, one fixture at a time in a work folder, compared as `(rule, line)` of the catalog's mapped rules. `expected-diff.txt` shares its file with the format mode; lint entries have the hadolint form (with a space in the key).

## invoke-formatter
`scripts/parity.sh format invoke-formatter` saves the PSScriptAnalyzer module at the catalog's version (`docs/parity/psscriptanalyzer.yaml`) with `Save-Module` into `<target>/parity/psscriptanalyzer-<version>/` on first use (needs PowerShell 7 `pwsh` and network; nothing is installed system-wide), fetches the PowerShell corpus and formats each file with `Invoke-Formatter` (`scripts/parity_invoke_formatter.ps1`: the CodeFormatting settings without PSUseCorrectCasing, which needs the command tables of the running PowerShell; a byte order mark stays, blank lines at the start and end of the output go) and with `sudsy format` under the folder's `sudsy.yaml` (Sudsy's defaults). The fixtures are the folder's own `*.ps1` and the corpus files (`corpus/<path>` in `expected-diff.txt`); trailing blanks are ignored on both sides (`ignore_trailing_blanks`: Invoke-Formatter keeps them). A file either tool rejects counts as a difference unless listed.

## csharpier
`scripts/parity.sh format shfmt` downloads the shfmt release executable at the catalog's `version` (`docs/parity/shfmt.yaml`) into `<target>/parity/shfmt-<version>/` on first use (needs network; Windows, Linux and macOS assets), fetches the shell corpus and formats each file with `shfmt <file>` (its defaults) and with `sudsy format` under the folder's `sudsy.yaml` (Sudsy's defaults, no preset). The fixtures are the folder's own `*.sh` and the corpus files (`corpus/<path>` in `expected-diff.txt`); a file shfmt or Sudsy rejects counts as a difference unless listed. 58 of the 82 files are identical; the others are listed with their reasons.

`scripts/parity.sh format csharpier` installs CSharpier at the catalog's `version` with `dotnet tool install --tool-path` into `<target>/parity/csharpier-<version>/`, formats every `.cs` in `tests/parity/csharpier/` with it and with `sudsy format` (the folder's `sudsy.yaml` extends `csharp/csharpier-compat`) and compares byte for byte, like the other format tools. The fixtures are `#if`/`#elif`/`#else` cases (nested, conditions with `&&`/`||`/`!`, inside statements, around whole files, branches no symbol set can activate); the large-scale comparison is the differential test ([testing.md](testing.md)).

## csharpier-xml
`scripts/parity.sh format csharpier-xml` formats with the same CSharpier (its XML formatter, default options) and with `sudsy format` under the folder's `sudsy.yaml` (`preset:xml/csharpier-compat`). The fixtures are the folder's own XML files, every file of `tests/fixtures/xml` (`fixtures/<file>`) and the project files of dotnet/aspnetcore (`tests/conformance/fetch-xml-projects.sh`, pinned, gitignored; named `corpus/<path>` in `expected-diff.txt`). CSharpier formats a copy, Sudsy the original; a file either tool rejects counts as a difference unless listed.

## dotnet-format
`scripts/parity.sh format dotnet-format` compares `sudsy format` with `dotnet format whitespace --folder` of the installed .NET SDK on `tests/parity/dotnet-format/`. A case is a `<case>.editorconfig` (the keys under test) and a C# source: `<case>.cs`, else the shared `input.cs`. Each side formats a copy of the source in a folder of its own that holds the case's `.editorconfig` as `.editorconfig` and the folder's `sudsy.yaml` (defaults), so the `.editorconfig` is the only input. Outputs are compared byte for byte; `expected-diff.txt` lists cases that may differ (`<case>: <reason>`), with the same stale-entry check as the other format modes. Nothing is installed; the run builds the debug CLI and worker.
