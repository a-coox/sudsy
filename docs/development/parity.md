# Differential testing against upstream tools

`scripts/parity.sh <tool>` runs the upstream tool and `sudsy lint` on the fixtures in `tests/parity/<tool>/` and compares the diagnostics as `(rule, line, column)`. The upstream rule name is mapped to a Sudsy rule id through the catalog (`docs/parity/<tool>.yaml`: the entries whose status is `rule <id>`); an upstream rule with no mapping is a mismatch. Every mismatch is printed (`only <tool>`, `only sudsy`) and the exit code is 1 when there is any. Run it from Git Bash.

Tools: <!-- generated:parity-tools -->`actionlint`, `buf`, `checkmake`, `eslint`, `eslint-jsonc`, `hadolint`, `markdownlint`, `psscriptanalyzer`, `shellcheck`, `stylecop`, `stylelint`, `stylelint-less`, `stylelint-scss`, `typescript-eslint`, `yamllint` (lint mode); `biome`, `buf`, `csharpier`, `csharpier-xml`, `dotnet-format`, `invoke-formatter`, `prettier`, `prettier-css`, `prettier-js`, `shfmt`, `taplo`, `terraform` (format mode, below).<!-- /generated --> Both modes install the tool at the catalog's `version` on first use and build the debug CLI; the install is data (see [Tool entries](#tool-entries)). yamllint is a pip package installed below `<target>/parity/yamllint-<version>/` (needs Python 3 and network).

## Fixtures
`tests/parity/<tool>/` holds one file per case plus the two configs that make the tools comparable: the upstream config (`.yamllint`) enables only rules Sudsy has an equivalent for, with the parameters Sudsy's rules take, and `sudsy.yaml` enables the matching Sudsy rules. A fixture is one file for every config, so the parameters must be the same for all cases. Fixtures where the tools legitimately differ are not included; those differences are recorded in the catalog entry's `gap`. Rules the formatter covers (yamllint `comments`) are off in `.yamllint`: they are tested as formatter output instead.

To add a case: add the file, enable the rule in both configs, run the script. To add a tool: add its entry to `scripts/parity_tools.json` ([Tool entries](#tool-entries)), a function to `scripts/parity_lint.py` that returns the upstream diagnostics as `{(rule, line, column)}`, and its fixtures.

## Differences lists
`tests/parity/<tool>/differences.yaml` records where Sudsy differs from the tool; the same file serves both modes of a tool.
```yaml
differences:            # each named difference once: <choice|gap>  <text>
  subst-indent: choice  multi-line `$(...)` keeps the source indentation
  for-no-in:    gap     tree-sitter-bash rejects `for x do`
files:                  # fixture key -> names; a lint key is `<file> <tool|sudsy>:<rule> <line>`
  corpus/bats-core/contrib/release.sh: subst-indent, array-indent
ratchet:                # a corpus too large to list: the least identical files; the group's name in `files` gives it a difference
  prettier-tests: 302
```
`choice` is intentional and documented (the `choice` names are the generated block `<!-- generated:differences:<tool> -->` of the language's `docs/formatting` page, written by `cargo xtask codegen`); `gap` is unintended, to fix, and stays out of the user docs. A text with `: ` or ` #` in it is quoted. The run fails on a differing file that is not listed (outside the ratchet groups), a listed file that no longer differs (stale), a name no file uses, a name that is not defined, and a ratchet group below its minimum; above it, the run prints the count to raise the minimum to. The report ends with the number of files per name, `choice` then `gap`, and the ratchet lines.

## eslint-jsonc
`scripts/parity.sh eslint-jsonc` uses ESLint 9 with eslint-plugin-jsonc (`docs/parity/eslint-plugin-jsonc.yaml`; needs Node), copies `tests/parity/eslint-jsonc/` to `work/` there so that `eslint.config.mjs` finds the plugin, and runs ESLint on every `.json` fixture. A fixture's name selects the rule and options: `eslint.config.mjs` enables one rule per fixture and `sudsy.yaml` enables the matching Sudsy rule through `overrides`, so both sides stay in step. `sorted-keys` and `sorted-array-values` report the entries that would have to move; where several shortest edits exist ESLint's pick can differ from Sudsy's, so fixtures stick to cases both agree on (the catalog `gap` says so).

## markdownlint
`scripts/parity.sh markdownlint` uses markdownlint-cli2 (needs Node), copies `tests/parity/markdownlint/` (the `.md` fixtures and a `.markdownlint.jsonc` that turns on only the rules Sudsy has an equivalent for) below its install folder and compares `(rule, line)` of every fixture: markdownlint reports a column for some rules only, so columns are not compared. The Sudsy rule of a `rule:` status stands for the MD id of the catalog entry.

## hadolint
`scripts/parity.sh hadolint` runs hadolint with `-f json` and `sudsy lint` (config: `tests/parity/hadolint/sudsy.yaml`, `preset:dockerfile/hadolint`) on the rule fixtures of the Dockerfile rules, `tests/rules/dockerfile/*/*.dockerfile` with their annotation lines removed, so the fixtures are not copied. `(rule, line)` is compared for the rules the catalog maps; hadolint's other codes (deferred DL rules, ShellCheck) are ignored. The rule fixtures are written to agree with hadolint; a case where it deliberately differs goes into its [differences](#differences-lists) (the lint key form).

## shellcheck
`scripts/parity.sh shellcheck` is the hadolint mode for shellcheck, run with `-s bash -o all -f json` (the optional checks are in the catalog, so they are on) and compared as `(rule, line)` with `sudsy lint` under `tests/parity/shellcheck/sudsy.yaml` (`preset:shell/shellcheck`) on `tests/rules/shell/*/*.sh` without annotations.

## checkmake
`scripts/parity.sh checkmake` is the hadolint mode for checkmake, run with a JSON line template on `tests/rules/makefile/*/*.mk` without annotations; `sudsy lint` runs under `tests/parity/checkmake/sudsy.yaml` (`preset:makefile/checkmake`). checkmake runs all its rules on every file, so a fixture is compared on the rule of its own folder only (`(rule, line)`), and the two rules checkmake reports a line late (`timestampexpanded`, and `minphony` at the `.PHONY` line, which it reads as a variable) are moved back. Fixtures with a `<name>.rules.yaml` set rule options and are left out.

## actionlint
`scripts/parity.sh actionlint` is the hadolint mode for actionlint, with the pinned corpus (`tests/conformance/fetch-github-actions-corpus.sh`: actionlint's own `testdata/ok`, `err` and `examples`, and the starter workflows). Each rule fixture (`tests/rules/github-actions/*/*.yml`, annotations removed) and each corpus file is copied to `.github/workflows/` of a work folder (a workflow is claimed by its folder), run through `actionlint -format '{{json .}}'` with the shellcheck and pyflakes integrations off, and through `sudsy lint`. An actionlint error becomes a catalog id from its `kind` and message (`actionlint_check` in `scripts/parity_lint.py`: `job-needs/cycle`, `expression/untrusted`, ...); the ids the catalog maps to a rule are compared as `(rule, line)`, the others are left out.

## psscriptanalyzer
`scripts/parity.sh psscriptanalyzer` uses the PSScriptAnalyzer module of invoke-formatter (needs `pwsh`) and runs `Invoke-ScriptAnalyzer` (`scripts/parity_psscriptanalyzer.ps1`) with the catalog's `rule:` entries that the preset `powershell/psscriptanalyzer` turns on, on the PowerShell rule fixtures (`tests/rules/powershell/*/*.ps1`, annotations removed) and the corpus (`tests/conformance/fetch-powershell-corpus.sh`), compared with `sudsy lint` (`tests/parity/psscriptanalyzer/sudsy.yaml`, that preset) as `(file, rule, line)`. It also checks that the catalog lists exactly the rules of `Get-ScriptAnalyzerRule`. A lint key is `corpus/<path> <psscriptanalyzer|sudsy>:<rule> <line>` (a fixture is `<folder>-<name>.ps1`).
## stylecop
`scripts/parity.sh stylecop` copies `tests/parity/stylecop/` (a net10.0 project referencing StyleCop.Analyzers at the catalog's version, plus `.cs` fixtures) to `target/parity/stylecop-plain/` and `stylecop-fixed/`, enables every catalog SA id of status `rule:` or `formatter`, or `option: csharp.format.<name>` for an option the `csharp/stylecop` preset sets, as a warning through a generated `.editorconfig`, and runs `dotnet build` with an SARIF error log. Two comparisons:
- plain: each `rule:` SA id, mapped through the catalog, must be reported by `sudsy lint` at the same `(rule, line, column)`, and `sudsy lint` must report nothing else of the mapped rules;
- fixed: after `sudsy fix --unsafe .`, StyleCop must report none of those formatter ids whose coverage is `covered` (in any fixture) or `partial` (in the `layout_*` fixtures; the older fixtures show their gap), and what it still reports for `rule:` ids must match `sudsy lint`.
The fixtures' `sudsy.yaml` extends `preset:csharp/stylecop`, so the formatter ids are checked under the preset's options and the `rule:` ids with the rules the preset enables. The `layout_*` fixtures are the layout rules' violations; the `doc_*` fixtures (summary, tags, wording, text) are the SA16xx documentation rules' cases, valid C# in which every partial type has only parts that StyleCop and Sudsy judge alike (StyleCop accepts one documented part, Sudsy checks each); the run prints the formatter ids no fixture violates (the build would pass vacuously for them). Needs the .NET SDK and network for the NuGet restore. To add a case, add a `.cs` file and enable its Sudsy rules in the preset (`crates/lang-csharp/presets/stylecop.yaml`); the catalog drives the id mapping.

## Tool entries
A tool is an entry of `scripts/parity_tools.json`, under `lint` or `format` (`parity_format.prepare` serves both modes), so installing one is config only (plus its `tests/parity/<tool>/` folder with `sudsy.yaml` and its `docs/parity/<name>.yaml` with the pinned `version`):
- `catalog`: the catalog file whose `version` pins the tool (`version_command` instead: the SDK's own, for `dotnet-format`); `install`: an `npm` package (`with`: more packages), a `pip` package, a `dotnet-tool`, a `psmodule` or a `release` (URL template, per-platform `assets`: a zip or tar archive, a gzip or the executable itself) and its `exe`, installed into `<target>/parity/<catalog>-<version>/` on first use (a lint entry may name a format entry whose install it shares: `"install": "buf"`);
- `needs`: `worker` builds the C# worker; `fetch`: scripts that fetch corpora.

## Format mode
One runner (`scripts/parity_format.py`) serves every format tool; an entry also has:
- `command`: the tool's command line with `{prefix}`, `{exe}` and `{file}`; `input`: `arg` (the file name is an argument), `stdin`, or `in-place` (the tool rewrites a copy); `tool_may_reject`: a file the tool rejects is a difference, not an error;
- `fixtures`: sources of fixtures, each a `dir` (default: the tool's folder) with `suffixes`, a fixture-name `prefix`, `recursive`, or a `list` file with `starts`; `kind: editorconfig-cases` is the `dotnet-format` layout below.

`scripts/parity.sh format prettier|biome` formats every JSON and YAML fixture in `tests/parity/<tool>/` with the tool (`prettier --no-config --no-editorconfig --embedded-language-formatting=off`, `biome format` with its defaults) and with `sudsy format`, and compares the outputs byte for byte. The tool is installed with npm at the catalog's `version` into `target/parity/<tool>-<version>/` on first use (needs Node and network); the fixtures are copied to `target/parity/<tool>-work/` first because `sudsy format` writes in place. The folder's `sudsy.yaml` extends the matching presets (`json/prettier-compat` and `yaml/prettier-compat`; `json/biome`), so a difference is a preset or formatter gap. Every difference is printed as a unified diff and the exit code is 1.

The `prettier` fixtures also include GraphQL: the folder's `.graphql` files and the corpus of `tests/conformance/fetch-graphql-corpus.sh` (`graphql/<repo>/<path>` in `differences.yaml`; Prettier's own tests in it include files it rejects, which count as differences unless listed, `tool_may_reject`). The `prettier` fixtures also include the folder's `.md` files, the repo's `docs/**/*.md` and the dotnet/runtime coding-guidelines docs (`tests/conformance/fetch-markdown-corpus.sh`, pinned); Prettier runs with `--embedded-language-formatting=off`, and the folder's `sudsy.yaml` sets `embedded_language_formatting: off`, because Sudsy's formatters of the fenced languages make other choices than Prettier's.

Fixtures that differ are listed in the folder's `differences.yaml` ([below](#differences-lists)). Fixtures named `crlf.*` keep CRLF line endings (`.gitattributes`: `-text`).

## buf
`scripts/parity.sh format buf` downloads the buf release executable at the catalog's `version` (`docs/parity/buf.yaml`) into `<target>/parity/buf-<version>/` on first use (needs network), fetches the Protobuf corpus (`tests/conformance/fetch-proto-corpus.sh`) and formats each file with `buf format <file>` (it has no options) and with `sudsy format` under the folder's `sudsy.yaml` (Sudsy's defaults, no preset). The fixtures are the folder's own `*.proto` and the corpus files (`corpus/<path>`). See [../formatting/protobuf.md](../formatting/protobuf.md) for the result.

`scripts/parity.sh buf` is the lint mode (hadolint's): `buf lint --error-format=json --path <fixture>` with the folder's `buf.yaml` (STANDARD) and `sudsy lint` (`preset:protobuf/buf-standard`) on `tests/rules/protobuf/*/*.proto` without annotations, one fixture at a time in a work folder, compared as `(rule, line)` of the catalog's mapped rules. ## terraform
`scripts/parity.sh format terraform` downloads the Terraform release zip at the catalog's `version` (`docs/parity/terraform.yaml`) into `<target>/parity/terraform-<version>/` on first use (needs network; Windows, Linux and macOS assets), fetches the HCL corpus (`tests/conformance/fetch-hcl-corpus.sh`) and formats each file with `terraform fmt -` (stdin) and with `sudsy fix` (`sudsy_command` in `scripts/parity_tools.json`: the runner's Sudsy side is `format` unless the tool says otherwise; here `terraform fmt` also rewrites `"${x}"` to `x`, which is the fix of the rule `deprecated-interpolation`, and the folder's `sudsy.yaml` turns the other rules off). The fixtures are the folder's own `*.tf` and the corpus's `*.tf` and `*.pkr.hcl` files (`corpus/<path>`); Nomad job files are left out because `terraform fmt` unwraps the `"${attr.kernel.name}"` that Nomad fills in at run time and Sudsy does not. ## invoke-formatter
`scripts/parity.sh format invoke-formatter` saves the PSScriptAnalyzer module at the catalog's version (`docs/parity/psscriptanalyzer.yaml`) with `Save-Module` into `<target>/parity/psscriptanalyzer-<version>/` on first use (needs PowerShell 7 `pwsh` and network; nothing is installed system-wide), fetches the PowerShell corpus and formats each file with `Invoke-Formatter` (`scripts/parity_invoke_formatter.ps1`: the CodeFormatting settings without PSUseCorrectCasing, which needs the command tables of the running PowerShell; a byte order mark stays, blank lines at the start and end of the output go) and with `sudsy format` under the folder's `sudsy.yaml` (Sudsy's defaults). The fixtures are the folder's own `*.ps1` and the corpus files (`corpus/<path>`); trailing blanks are ignored on both sides (`ignore_trailing_blanks`: Invoke-Formatter keeps them). ## dotnet-format
`scripts/parity.sh format dotnet-format` compares `sudsy format` with `dotnet format whitespace --folder` of the installed .NET SDK on `tests/parity/dotnet-format/`. A case is a `<case>.editorconfig` (the keys under test) and a C# source: `<case>.cs`, else the shared `input.cs`. Each side formats a copy of the source in a folder of its own that holds the case's `.editorconfig` as `.editorconfig` and the folder's `sudsy.yaml` (defaults), so the `.editorconfig` is the only input. Outputs are compared byte for byte; `differences.yaml` lists the cases that differ. Nothing is installed; the run builds the debug CLI and worker.

## prettier-js
`scripts/parity.sh format prettier-js` is the `prettier` entry (same install, `--no-config`, embedded formatting off) for JavaScript and TypeScript, with the Sudsy side under the folder's `sudsy.yaml` (defaults) and the corpus of `tests/conformance/fetch-js-corpus.sh` (pinned, gitignored): Prettier's own `tests/format/{js,jsx,typescript}` inputs at the catalog's tag (no `_errors_`, snapshot or Flow-typed files) and slices of real projects (vuejs/core, docusaurus, excalidraw, MUI, lodash, three.js, express, the TypeScript compiler, vscode's `base`), formatted by Prettier with its defaults. The run is parallel and prints only the differing files (`PARITY_FILTER=<name substring>` runs those fixtures alone with their diffs).
- Both corpora are `ratchet` groups (`prettier-tests`, `real-world`): files are counted (identical, different, rejected by Prettier), not listed. The real-world group carries the gap `project-options`: Prettier runs with `--no-config`, so a project's own Prettier options are not applied (the corpus fetches no config files and Sudsy's JS options are not mapped yet).

## prettier-css
`scripts/parity.sh format prettier-css` is `prettier-js` for CSS, SCSS and Less (`--no-config`; the Sudsy side runs under the folder's `sudsy.yaml`, defaults) over the corpus of `tests/conformance/fetch-css-corpus.sh` (pinned, gitignored): Prettier's own `tests/format/{css,scss,less}` inputs at the catalog's tag, and real projects (Bootstrap 5.3.3 scss and dist css, Bulma 1.0.2, ant-design 4.24.16 and Semantic UI 2.5.0 less, normalize.css, the docusaurus 3.9.2 theme css). The ratchet groups are `prettier-css`, `prettier-scss`, `prettier-less` (one per Prettier folder; the `.css` fixtures that hold SCSS or Less syntax on purpose are parse failures that stay in the count) and `real-world` (gap `project-options`, as for JS).

## stylelint
`scripts/parity.sh stylelint|stylelint-scss|stylelint-less` is the eslint mode for stylelint (needs Node): a config enables the catalog's `rule:` entries (`docs/parity/stylelint*.yaml`; the plugin and `postcss-scss`/`postcss-less` as the dialect parser come with the tool's `install`), stylelint runs with `-f json` (its report is on stderr) on the rule fixtures `tests/rules/<css|scss|less>/*/*.<ext>` (annotations removed), and `sudsy lint` runs under `tests/parity/<tool>/sudsy.yaml`; `(rule, line)` is compared. Until a catalog entry maps to a Sudsy rule the run prints the fixture count only. Core rules run with `true`: a rule that needs a primary option gets it in the runner's config when it is mapped.

## eslint
`scripts/parity.sh eslint` is the hadolint mode for ESLint 9 (needs Node): a flat config enables the catalog's `rule:` entries (`docs/parity/eslint.yaml`) with their default options, ESLint runs with `-f json` on `tests/rules/js/*/*.js` (annotations removed) and on the real-world `.js` files of the JS corpus, and `sudsy lint` runs under `tests/parity/eslint/sudsy.yaml` (the preset `js/eslint-recommended`); `(rule, line, column)` is compared. Both tools read a `.js` as a module, which rejects `with`, octal numbers and the like: a file is copied as `.mjs` when a line starts with `import` or `export`, else as `.cjs` (a script). Known differences are listed in `tests/parity/eslint/differences.yaml` (`<fixture> <eslint|sudsy>:<rule> <line>`). ESLint runs once over every file, not once per file, with `noInlineConfig` (Sudsy does not read `eslint-disable` comments, which the corpus has).

`scripts/parity.sh typescript-eslint` is the same run for typescript-eslint's non-type-aware rules (`docs/parity/typescript-eslint.yaml`, pinned at its `version`, installed with ESLint 9.39.5): the flat config sets typescript-eslint's parser for `.ts` and `.tsx` files, enables the catalog's `rule:` entries as `@typescript-eslint/<name>` with their default options, and runs on `tests/rules/js/*/*.ts|tsx` and on the `.ts` and `.tsx` files of the real-world part of the JS corpus (Prettier's own tests are left out, as for `eslint`). A file the parser rejects is left out and counted in the first line of the output. Sudsy runs under `tests/parity/typescript-eslint/sudsy.yaml` (the preset `js/typescript-eslint-recommended` and the catalog's rules that preset does not enable); differences are in `tests/parity/typescript-eslint/differences.yaml`.
