# Adding a language with tree-sitter

A language whose tree-sitter grammar exists and is good enough costs a grammar file, a node-name table, a small formatter and about 20 lines of provider glue; the parser, error recovery and lossless tree come from `core-treesitter`. `lang-toml` is the worked example (`lang-xml` adds a layout of its own and well-formedness checks) (a grammar of 50 lines, a mapping of 50, a provider of 33, against about 880 for the hand-written JSON parser and formatter). Hand-written parsers stay the choice where speed, error messages or recovery matter (C#, JSON, YAML); a hand-written parser can replace a tree-sitter one later without touching anything outside the language crate, because the core sees only our tree.

## What the adapter does (`core-treesitter`)
`Engine::new(language, grammar, mapping)` parses with a linked-in tree-sitter `Language` (native C, no Wasm: the Wasm host would link a second wasmtime) and converts the result:
- Every tree-sitter node named in `Mapping::kinds` becomes the kind of our grammar it maps to: a node kind becomes a node, a token kind a leaf (its tree-sitter children are swallowed, so a string with escape sequences is one token; an `ERROR` inside it is reported only if the token is tagged `#checked`), a trivia kind (comments) trivia. An unmapped node with children is transparent; an unmapped leaf is an `Unknown` error token.
- Tree-sitter's tree has no whitespace or newlines: the bytes between tokens are rebuilt as `Whitespace` and `Newline` tokens and attached by the shared trivia rule, so the tree prints back to the input byte for byte. Text that is neither is an `Unknown` token.
- `ERROR` nodes become `SyntaxKind::ERROR` and a parse error, `MISSING` nodes a parse error. Messages are "syntax error" and "missing X", with no codes or hints.
- `Mapping::wrap`: tree-sitter hides one-part keys and literals as bare tokens, while shapes (`#delimited-list`, `#key-value`) want nodes as items. A token listed there is wrapped in a node of its own, unless its tree-sitter parent already maps to that node.
- A zero-width `Eof` token ends the root; it owns the comments at the end of the file.

## Steps
1. **Grammar file** `grammars/<lang>.grammar` (format: [syntax-tree.md](syntax-tree.md)). Take a free language id (`language <name> <id> "<Display name>"`, 4 bits; codegen refuses a duplicate). Declare the trivia tokens (`Whitespace`, `Newline`, the comment kinds), `Eof` and `Unknown #error`, one token per tree-sitter token you keep, and the nodes with the tags the shared code reads: `#delimited-list`, `#block`, `#key-value`, `#separator`, `#mapping`, `#sequence`. Read the grammar's `node-types.json` first: hidden rules (`_name`) are not nodes in the tree, so their children are tokens in the parent.
2. **Crate** `crates/lang-<name>` (a workspace member by the `crates/*` glob). `Cargo.toml` with the tree-sitter grammar crate, `core-treesitter`, `core-config`, `core-format`, `core-rules`, `core-syntax`, `provider-api`, and `build = "../../build/lang-crate.rs"` (embeds `rules/*.yaml`). `src/mapping.rs` (the `Mapping` table), `src/format.rs` (option schema from the `shared::` options plus the language's own, a `NodeFormatter` for the nodes whose tag default is not right, presets), `src/rules.rs` (`RULES`, the Rust rules; empty to start), `src/hooks.rs` (`RuleHooks`: keys and scalars for the shared rules), and `src/lib.rs` (with `core_syntax::include_generated!();` for the typed wrappers: `generated`, written by the build script from the grammar) and one `pub fn provider() -> TreeSitterProvider` filling a `core_treesitter::Spec` (tree-sitter language, grammar, mapping, extensions and exact file names (`.editorconfig`; a trailing `*` matches a prefix, `Dockerfile.*`), schema, formatter, hooks, rules, `provider_api::pattern_files!()` and an optional `validate` function for semantic checks).
3. **Register**: `lang-<name>` in `crates/languages/Cargo.toml` and one line in `languages::providers()`. Nothing else names the language: the grammar registry (`core_syntax::grammars`) and the crate's `generated` module (kind constants, AST wrappers, the grammar hash) come from the build scripts, and the config schema, the docs' rule and option tables, the language lists of the README, the overview and the editor docs (`<!-- generated:languages -->`), and the VS Code activation events and document selector (`editors/vscode/src/selector.generated.ts`, from the providers' file matchers) from `cargo xtask codegen`. Add `docs/formatting/<name>.md` with a `<!-- generated:options -->` block. Shared comment rules and `max-line-length` work through the grammar tags with no code. `cargo xtask new-rule <name> <id>` needs the language's `starter.<Kind>.<ext>` ([../development/testing.md](../development/testing.md)).
4. **Pattern rules**: `crates/lang-<name>/rules/*.yaml` are built-in rules with no further code ([../rules/patterns.md](../rules/patterns.md)).
5. **Tests**: format fixtures under `tests/fixtures/<name>/` (lossless tree, trivia attachment, and `core_format::testing::check`: round trip, meaning, idempotency, comments kept), unit tests for the layout, the language's conformance suite as an ignored test with a fetch script in `tests/conformance/` (pinned commit, gitignored corpus).
6. **Measure**: committed input files in `bench/inputs/<ext>/` (the folder is named after the files' extension; `perf-bench list` finds the provider by it, and `bench.sh` measures what it lists) and record parse and format throughput, binary size and build time in [../performance/numbers.md](../performance/numbers.md).
7. **Docs**: [overview.md](overview.md) (the parser row), the presets list, the roadmap. **Parity** with an upstream formatter: an entry in `scripts/parity_format.json` ([../development/parity.md](../development/parity.md)).

## Per-language cost and limits
- Code: grammar file about 40 lines, mapping about 50, provider glue about 20, formatter about 130 for TOML. Expect more formatter code for a language with irregular layout; the shapes cover lists, key-values, blocks and statement sequences.
- Cost in every build: a C compiler (already needed), the tree-sitter runtime once, and the grammar's `parser.c` and scanner per language; sizes are in `numbers.md`.
- Tree-sitter is 4-10x slower than the hand-written parsers and its trees need the adapter pass; the printer dominates the end-to-end cost anyway.
- A grammar that lags its language spec (TOML 1.1 today) needs a fork or an upstream fix, which the language then carries. Tree-sitter accepts documents that are syntactically fine and semantically invalid (duplicate keys, bad dates); the provider checks those after the parse and reports them as parse errors (`lang-toml/src/validate.rs`), so such a file is refused like a syntax error.
- Error recovery is tree-sitter's: a bad line may swallow a large span into one `ERROR`. The formatter refuses a file with errors, so this only affects messages.
- Not covered by the adapter: incremental reparse, a depth limit (the walk is iterative; the formatter recurses), dialects, embedded code in another language (Markdown fences, Razor).

## Composite languages
A language made of several tree-sitter grammars (`lang-markdown`: the block grammar, and the inline grammar inside its `inline` and `pipe_table_cell` nodes) passes a `core_treesitter::Composite` to `TreeSitterProvider::with_composite`; the grammar file and the formatter stay one per language.
- `Injected { host, language, mapping }`: when the converter enters a node named `host`, it parses the node's text with the second grammar (`set_included_ranges`: the host range minus the host's own named children, which are the block continuations of quotes and lists) and scans the result with the second mapping in place of the host's children. The carved-out children are emitted as trivia where they fall. One parser pool per injected grammar; the second tree is dropped after the walk, so the cost is one extra parse per host node and a second mapping table.
- `text`: the kind of the token for text no mapped node covers, one token per line with its blanks trimmed; an unmapped leaf is then text, not an error. `continuation`: a `\` that ends a line (alone or after a blank) is whitespace trivia, not text (shell line continuations; `lang-shell` is a composite with no injected grammar). The converter tracks the end of what it has emitted and fills the gaps before each node and at each exit.
- `refine`: a mapped token whose text starts with a prefix is another kind (`<!--` makes an HTML block or tag an `HtmlComment`, a `#comment` token, so suppression comments and `no-empty-comment` work).
- Pattern rules match nodes only: wrap a token a rule needs in a node with `Mapping::wrap`.
- Embedded code in another language (the code of a fence) would be one more `Injected` whose mapping targets that language's grammar kinds; none exists yet.
