# Adding a language with tree-sitter

A language whose tree-sitter grammar exists and is good enough costs a grammar file, a small formatter and a `lang.yaml` with a node-name table (the table, the provider glue and `Cargo.toml` are generated from it); the parser, error recovery and lossless tree come from `core-treesitter`. `lang-toml` is the worked example (`lang-xml` adds a layout of its own and well-formedness checks) (a grammar of 50 lines, a `lang.yaml` of 50, against about 880 for the hand-written JSON parser and formatter). Hand-written parsers stay the choice where speed, error messages or recovery matter (C#, JSON, YAML); a hand-written parser can replace a tree-sitter one later without touching anything outside the language crate, because the core sees only our tree.

## What the adapter does (`core-treesitter`)
`Engine::new(language, grammar, mapping)` parses with a linked-in tree-sitter `Language` (native C, no Wasm: the Wasm host would link a second wasmtime) and converts the result:
- Every tree-sitter node named in `Mapping::kinds` becomes the kind of our grammar it maps to: a node kind becomes a node, a token kind a leaf (its tree-sitter children are swallowed, so a string with escape sequences is one token; an `ERROR` inside it is reported only if the token is tagged `#checked`), a trivia kind (comments) trivia. An unmapped node with children is transparent; an unmapped leaf is an `Unknown` error token. A `from` is the node's name; when a grammar has a rule and a keyword of the same name (protobuf's `message`), write the keyword's entry quoted as in tree-sitter queries (`"\"message\""` matches only the anonymous node, `message` only the named one; with no quoted entry the name matches both).
- Tree-sitter's tree has no whitespace or newlines: the bytes between tokens are rebuilt as `Whitespace` and `Newline` tokens and attached by the shared trivia rule, so the tree prints back to the input byte for byte. Text that is neither is an `Unknown` token.
- `ERROR` nodes become `SyntaxKind::ERROR` and a parse error, `MISSING` nodes a parse error. Messages are "syntax error" and "missing X", with no codes or hints.
- `Mapping::wrap`: tree-sitter hides one-part keys and literals as bare tokens, while shapes (`#delimited-list`, `#key-value`) want nodes as items. A token listed there is wrapped in a node of its own, unless its tree-sitter parent already maps to that node.
- A zero-width `Eof` token ends the root; it owns the comments at the end of the file.

## Steps
1. **Grammar file** `grammars/<lang>.grammar` (format: [syntax-tree.md](syntax-tree.md)). Take a free language id (`language <name> <id> "<Display name>"`, 1 to 31; codegen refuses a duplicate). Declare the trivia tokens (`Whitespace`, `Newline`, the comment kinds), `Eof` and `Unknown #error`, one token per tree-sitter token you keep, and the nodes with the tags the shared code reads: `#delimited-list`, `#block`, `#key-value`, `#separator`, `#mapping`, `#sequence`. Read the grammar's `node-types.json` first: hidden rules (`_name`) are not nodes in the tree, so their children are tokens in the parent.
2. **Crate** `crates/lang-<name>` (a workspace member by the `crates/*` glob). Cargo needs a manifest before `cargo xtask codegen` can write the real one: create `src/lib.rs` (empty) and a `Cargo.toml` of `[package]` and `name = "lang-<name>"`. Then write `lang.yaml` and run `cargo xtask codegen`; it generates `Cargo.toml` (the shared dependencies, `build = "../../build/lang-crate.rs"` which embeds `rules/*.yaml` and writes `generated`, the `static-grammars` feature) and `src/provider.generated.rs` (`pub fn provider() -> TreeSitterProvider` filling a `core_treesitter::Spec`). Keys of `lang.yaml`:

   - `grammar-crate` and `grammar-version` (the tree-sitter crate: a workspace dependency of the root `Cargo.toml`, `optional` behind the default `static-grammars` feature; `grammar-default-features: false` for a crate whose defaults are unwanted); `grammar-path` instead of `grammar-version` for a fork in `grammars/tree-sitter-<lang>/`, see [../development/grammar-forks.md](../development/grammar-forks.md)), `language-const` (default `LANGUAGE`; the language is `core_packs::language!("<name>", <crate>::<const>)`), `inline-language-const` (a second grammar a pack exports as `sudsy_language_inline`).
   - `extensions` and `file-names` (exact names such as `.editorconfig`; a trailing `*` matches a prefix, `Dockerfile.*`; `cargo xtask codegen` rejects an entry two languages share), `formatter` (the `NodeFormatter` type, re-exported from `lib.rs`).
   - Optional: `mapping` (below; a string names a hand-written `Mapping` instead, default `mapping::MAPPING`), `composite` (a map `text`, `continuation`, `tolerant` for a `Composite` with no injected grammar, see below; a string names a hand-written one), `hooks` (default `core_rules::DEFAULT_HOOKS`), `families`, `validate` (a function for semantic checks), `embedded` (finds code of other languages, see below), `options` and `presets` (below), `deps` and `dev-deps` (workspace dependencies beyond the shared ones).

   By hand: `src/format.rs` (`include!("schema.generated.rs");` for the option schema and its name consts, and a `NodeFormatter` for the nodes whose tag default is not right), `src/rules.rs` (`RULES`, the Rust rules; empty to start), optionally `src/hooks.rs` (`RuleHooks`: keys and scalars for the shared rules), and `src/lib.rs`: the doc comment, the `mod` lines, `pub use format::{..., option_schema};` and `include!("provider.generated.rs");` (which also holds the typed wrappers `generated`, written by the build script from the grammar).
   `options` is the formatter's option schema, in order, and `presets` the names of `presets/<name>.yaml` files (`<language>/<name>`); codegen writes `src/schema.generated.rs` (one const per option, `option_schema()` with the presets), which the crate includes where its formatter lives. An entry is `indent_style` or `end_of_line` (shared, no argument), `line_width: 80` (a shared option with its default; `max_blank_lines: [1, "doc"]`), or `name: {values: [...] | range: [min, max] | kind: words | kind: word-sets, default: ..., doc: ...}` (a choice, an integer, a word list, a list of word lists; with none of these a boolean). Hand-written languages (JSON, YAML, C#) have a `lang.yaml` of these two keys only. Validation beyond the declared kind is not expressed here: the schema has none today.
   `mapping` is a map from a grammar kind to the tree-sitter node names it takes (a list, or one string split on blanks; a keyword that shares its name with a rule is quoted, `'"message"'`): `Keyword: 'if then fi'`. `wrap: {Token: Node}` is `Mapping::wrap`; `same: 'table pair'` lists names whose kind is the same name in Pascal case (`table` is `Table`). Every grammar token with fixed text also takes the anonymous tree-sitter token of that text with no entry (`token LBracket "["`); an entry for the same name wins. Codegen writes the `Mapping` (and the `Composite` of a `composite` map) into `provider.generated.rs`. A table with logic (`lang-markdown`: injected grammars with closures) stays Rust in `src/mapping.rs`, named by string.
3. **Register**: nothing by hand. `cargo xtask codegen` fills the `generated:` regions (`# generated:NAME` ... `# /generated`) of the root `Cargo.toml` (grammar and language dependencies), `crates/languages` (dependencies, `static-grammars`, `providers()`), `crates/pack` (dependencies, features, `exports!`) and `scripts/pack.sh`, from every `lang.yaml` (see [language-packs.md](language-packs.md)) (it re-runs itself once in a build that has the new language); `--check` fails until the regions are current. Nothing else names the language: the grammar registry (`core_syntax::grammars`) and the crate's `generated` module (kind constants, AST wrappers, the grammar hash) come from the build scripts, and the config schema, the docs' rule and option tables, the language lists of the README, the overview and the editor docs (`<!-- generated:languages -->`), and the VS Code activation events and document selector (`editors/vscode/src/selector.generated.ts`, from the providers' file matchers) from `cargo xtask codegen`. Add `docs/formatting/<name>.md` with a `<!-- generated:options -->` block. Shared comment rules and `max-line-length` work through the grammar tags with no code. `cargo xtask new-rule <name> <id>` needs the language's `starter.<Kind>.<ext>` ([../development/testing.md](../development/testing.md)).
4. **Pattern rules**: `crates/lang-<name>/rules/*.yaml` (no `language:` key) are built-in rules with no further code ([../rules/patterns.md](../rules/patterns.md)).
5. **Tests**: `tests/<name>.rs` is a `fmt` helper over `provider_api::format_testing` (`assert_formats(provider, "a.ext", input)`: round trip, meaning, idempotency, comments kept; `Formatting` for a subject with options), `assert_file_names` for the file matchers, `check_corpus(provider, "a.ext", "<name>", &["ext"])` for the ignored conformance test, and one test per layout rule; `tests/rule_fixtures.rs` is the six-line copy of any other language's. The corpus fetch script in `tests/conformance/` (pinned commits, gitignored corpus) is `source tarball-corpus.sh` and a `fetch_tarballs <name>` list of `repo sha tar-pattern...` lines (copy `fetch-shell-corpus.sh`).
6. **Measure**: committed input files in `bench/inputs/<ext>/` (the folder is named after the files' extension; `perf-bench list` finds the provider by it, and `bench.sh` measures what it lists) (150 KB at most per language) and record parse and format throughput, binary size and build time in [../performance/numbers.md](../performance/numbers.md).
7. **Docs**: [overview.md](overview.md) (the parser row), the presets list, the roadmap. **Parity** with an upstream formatter: an entry in `scripts/parity_tools.json` ([../development/parity.md](../development/parity.md)).

## Per-language cost and limits
- Code: grammar file about 40 lines, `lang.yaml` with the mapping about 40, formatter about 130 for TOML. Expect more formatter code for a language with irregular layout; the shapes cover lists, key-values, blocks and statement sequences.
- Cost in every build: a C compiler (already needed), the tree-sitter runtime once, and the grammar's `parser.c` and scanner per language; sizes are in `numbers.md`.
- Tree-sitter is 4-10x slower than the hand-written parsers and its trees need the adapter pass; the printer dominates the end-to-end cost anyway.
- A grammar that lags its language spec (TOML 1.1 today) needs a fork or an upstream fix, which the language then carries. Tree-sitter accepts documents that are syntactically fine and semantically invalid (duplicate keys, bad dates); the provider checks those after the parse and reports them as parse errors (`lang-toml/src/validate.rs`), so such a file is refused like a syntax error.
- Error recovery is tree-sitter's: a bad line may swallow a large span into one `ERROR`. The formatter refuses a file with errors, so this only affects messages.
- Not covered by the adapter: incremental reparse, a depth limit (the walk is iterative; the formatter recurses), dialects.

## Composite languages
A language made of several tree-sitter grammars (`lang-markdown`: the block grammar, and the inline grammar inside its `inline` and `pipe_table_cell` nodes) passes a `core_treesitter::Composite` to `TreeSitterProvider::with_composite`; the grammar file and the formatter stay one per language.
- `Injected { host, language, mapping }`: when the converter enters a node named `host`, it parses the node's text with the second grammar (`set_included_ranges`: the host range minus the host's own named children, which are the block continuations of quotes and lists) and scans the result with the second mapping in place of the host's children. The carved-out children are emitted as trivia where they fall. One parser pool per injected grammar; the second tree is dropped after the walk, so the cost is one extra parse per host node and a second mapping table.
- `text`: the kind of the token for text no mapped node covers, one token per line with its blanks trimmed; an unmapped leaf is then text, not an error. `continuation`: a `\` that ends a line (alone or after a blank) is whitespace trivia, not text (shell line continuations; `lang-shell` is a composite with no injected grammar). The converter tracks the end of what it has emitted and fills the gaps before each node and at each exit. `tolerant`: tree-sitter node names whose descendants' syntax errors are not reported (the text stays in the tree), for a language that turned tokens, which swallowed such errors, into nodes.
- `refine`: a mapped token whose text starts with a prefix is another kind (`<!--` makes an HTML block or tag an `HtmlComment`, a `#comment` token, so suppression comments and `no-empty-comment` work).
- Pattern rules match nodes only: wrap a token a rule needs in a node with `Mapping::wrap`.

## Embedded languages
Code of one language inside a file of another (shell in a Dockerfile `RUN`, the code of a Markdown fence) is parsed with that language's own provider and checked by its own rules; the host never re-reads it by hand. The host only says where the code is.
- A host declares regions: `embedded: <fn>` in `lang.yaml` names a function `fn(&SyntaxNode, &str) -> Vec<core_syntax::Embedded>` (`TreeSitterProvider::with_embedded`; any other provider implements `LanguageProvider::embedded`). An `Embedded` holds the language (a language name or a file extension, resolved by `provider_api::embedded::resolve` among the providers), the range in the host file, `carved` (the host's own parts inside the range: the quote and indentation prefix of each fence line, the comment lines of a continued `RUN`), and `format` (whether the host lets the language's formatter rewrite the code). The two examples are `lang-dockerfile/src/embedded.rs` and `lang-markdown/src/format/embedded.rs`.
- The engine parses the range with the carved parts blanked to spaces (`Embedded::blanked`: same length, so an offset in the parse is an offset from the start of the range). A language nobody handles, a provider with a worker process (`embeddable()`), and code with syntax errors are left out: the code stays as written.
- Lint (`core-incremental`, the `lint` query): the embedded language's rules run on its parse with that language's config section (`FileInput::language`), its suppression comments, and the same path; positions, related spans and fixes are moved to the host file, and a fix that would touch a carved part or add a line break to a region with carved parts is dropped. The host's suppression comments apply to the result. Rules need no change.
- Host rules read the parses through `FileContext::embedded` (`EmbeddedTree`: range, language name, root): the Dockerfile `run-command` family reads the commands of a `RUN` from the Shell tree. A rule fixture run of such a host names the companion providers: `provider_api::fixtures::rule_fixtures_with(&host, &[&companion])`.
- Format (the `format` query): when the host's options do not turn it off (`embedded_language_formatting`, declared by the host's schema), each region with `format` is formatted by its language's formatter on the code without the carved parts, and put back with the first code line's host prefix on every line. This runs on the host's output, which is parsed again to find the regions; if the regions changed, the host's output stays. The host formatter itself never sees the other language: a host that does not set `format` (Dockerfile) keeps the code as written.
- A host whose regions never set `format` (`LanguageProvider::formats_embedded` false: Dockerfile and Markdown still walk, GitHub Actions says no) is not walked by `format`.
- Cost: a host that reports no regions pays one call returning an empty list; a region costs one parse of the other language, and its rules one run.
